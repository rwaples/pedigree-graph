# Slice 5d pair-kinship memo gate

What keeping the recurrence memo on the graph buys and costs on `random_30k`:
the first degree-3 `pair_kinship` on a fresh graph before and after the slice,
the same query again on the same graph, and `relationship_kinship_matrix`
after a warm walk.

## Method

Every figure below was produced by `benchmarks/bench_pair_kinship.py`, which
is committed so these numbers can be reproduced and challenged:

```bash
cd external/pedigree-graph
pixi run python benchmarks/bench_pair_kinship.py --repeat 3 --out benchmarks/reports/pair_kinship.json
pixi run python benchmarks/bench_pair_kinship.py --render benchmarks/reports/pair_kinship.json
```

Run these from inside the checkout. `pixi run --manifest-path <path>` selects
the environment but leaves the working directory at the umbrella root, so the
relative paths above do not resolve under it.

Each cell runs in a fresh single-threaded subprocess, three times, interleaved,
and the tables quote the median with the observed spread. Peak RSS is the
kernel's `VmHWM`, reset through `/proc/self/clear_refs` at the start of the
timed region, so a warm cell's RSS is the process footprint while the retained
memo is resident, not the growth of the timed call. Fixture construction,
pair extraction and, for the warm arms, the untimed first walk all happen
before the region.

The pre-slice side of the comparison is the same benchmark file run against a
detached worktree of `f7259a9`, the last commit before this slice, with only
the `cold` cell selected (`--only random_30k/cold`). On that tree the warm arms
would measure a second cold call, which the earlier slice notes already record.
The cold `relationship_kinship_matrix(max_degree=3)` figure is taken from
`benchmarks/matrix_exactification.md` rather than re-run here; its checksum
matches the warm matrix cell below.

`benchmarks/.gitignore` excludes `reports/`, so the raw JSON is local-only and
this note carries the environment and spread inline.

### Discarded runs

A first sweep on 2026-09-07 was discarded. Every cell after its first took
about 290 s instead of about 88 s, and the cause was the host, not the code:
every core sat at 800 MHz under full load (`scaling_cur_freq`), while the
governor, profile and turbo settings all reported a 2.6 GHz ceiling. The
harness records the CPU's configured maximum, not its live clock, so a clamp
like this does not show in the environment block. Both sweeps below were run
after the clock had returned to 2.6 GHz and it was checked again at the end of
each.

## Input

Generated by `tests/parity/pedigrees.py`; the benchmark takes the parameters
from that module rather than re-declaring them.

| fixture | rows | parameters | input SHA-256 |
|---|---:|---|---|
| `random_30k` | 30,300 | seed 30000, 1,500 founders, 8 generations, 3,600 per generation | `f4d558a6957b9c12efe4a28778448a9b981769a5998c039849bbcec316d0b80d` |

The degree-3 query is 566,714 pairs. Its closure is 23,106,454 memo entries in
a 2**25-slot table, 384 MiB, which is what the graph retains after the walk.

## Results

Pre-slice, `f7259a9`:

| input | strategy | reps | wall (median) | spread | peak RSS (median) | checksum |
|---|---|---:|---:|---:|---:|---|
| `random_30k` | degree-3 pair_kinship, fresh graph | 3 | 87.44 s | 0.4% | 786 MiB | `11925760` |

Post-slice:

| input | strategy | reps | wall (median) | spread | peak RSS (median) | checksum |
|---|---|---:|---:|---:|---:|---|
| `random_30k` | degree-3 pair_kinship, fresh graph | 3 | 82.96 s | 0.1% | 784 MiB | `11925760` |
| `random_30k` | the same query again on the same graph | 3 | 0.45 s | 1.5% | 598 MiB | `11925760` |
| `random_30k` | the same matrix after a degree-3 pair_kinship | 3 | 1.27 s | 1.5% | 647 MiB | `12021248` |

The individual cold runs were 87.49, 87.17 and 87.44 s before and 82.88, 82.97
and 82.96 s after: disjoint ranges, ratio 0.95, so under the ADR 0007 rule this
is a confident pass rather than noise. Peak RSS moved from 786 to 784 MiB.

For the matrix, `benchmarks/matrix_exactification.md` records
`relationship_kinship_matrix(max_degree=3)` on a fresh graph at 84.60 s and 808
MiB with checksum `12021248`; after a warm degree-3 walk the same matrix, same
checksum, costs 1.27 s. The memo grew from 23,106,454 to 23,114,008 entries
during it: the diagonal's closure was already almost entirely inside the
pair closure, which is why the matrix used to pay the whole 31 s self-pair
walk again for nothing.

## The kernel shape that was rejected

The first implementation handed the memo tables into the numba kernel as
arguments, let the kernel grow them in place and returned them. Same bits,
same checksum, and a confident 6.4% cold regression: 93.13, 92.95 and 93.00 s
against the 87.44 s baseline, with RSS unchanged at 787 MiB. Splitting the
walk into an always-inlined body with separate cold and warm entry points, so
the cold path's tables were again local allocations, did not recover it
(93.49, 93.39 and 93.27 s). Returning the arrays from the kernel is what
costs; why LLVM generates a slower loop for it was not chased further, since
ADR 0007's Rust port replaces this kernel.

The landed shape is the one that measures fastest: the kernel takes a
caller-owned table, mutates it in place, never allocates, grows or returns it,
and stops with `overflow = 1` when the load factor would be exceeded.
`_run_kernel` then doubles the table and re-enters. A restart is cheap because
every node resolved before it is already a memo hit, and the number of
restarts is the number of doublings: the table starts at four slots per
requested pair, 2**22 here, and reaches 2**25, so three.
That shape is 5% faster than the pre-slice kernel on the cold walk, so the
memo comes with no cold cost at all.

## What the numbers mean for a caller

- A second `pair_kinship` on the same graph costs its new pairs, not its
  closure: 0.45 s instead of 83 s for a repeat, on a query whose closure is
  the whole deep end of the pedigree.
- `relationship_kinship_matrix` after `pair_kinship`, or the other way round,
  no longer walks the closure twice. The matrix after a warm walk is 1.27 s.
- The price is 384 MiB resident for the life of this graph. The default
  retention limit is 1 GiB (`_MEMO_RETAIN_LIMIT`); a table over it is dropped
  after the call rather than raised on, and `_release_kinship_matrices` drops
  it on demand.
- The 0.7.1 adapter `compute_pair_kinship`, which is what pedsum and fitACE
  call today, does not retain the memo. Their resident memory after the call
  is what it was before this slice; the saving is available once they move to
  `pair_kinship`.
